## Sandbox kapasitesi: create/start ve çalışma sırasında host süreci çökmesi

- [İlk gerçek Docker karşı örneği](review-evidence/sandbox-admission-crash-before.json), yalnız flock kullanan runner'ın SIGKILL sonrasında kapasiteyi erken bıraktığını gösterdi: ilk konteyner hâlâ çalışırken ikinci runner başlayabildi. Deneme 128 MiB/0.25 CPU sınırında yapıldı.
- [Güncel gerçek Docker kontrolü](review-evidence/sandbox-admission-crash-review.json) beş SIGKILL penceresini geçti: intent yazıldıktan sonra create öncesi, create yanıtından sonra ID kalıcılaşmadan önce, ID kalıcılaştıktan sonra start öncesi, çalışan aday sırasında ve konteyner/dizin temizlendikten sonra intent silinmeden önce. Running fixture 45 saniyelik aday ve 60 saniye faz bütçesi kullanır; kurtarma adayın doğal bitişini beklemeden 20 saniyelik reconcile süresi içinde tamamlandı. Her senaryoda ikinci runner başlamadan eski konteyner ve exact inode kayıtlı çalışma dizini kaldırıldı. Önceki ve yeni runner farklı work root kullandı; önceki root içindeki ilgisiz dosya ve aynı label anahtarını farklı nonce ile taşıyan bağımsız sentinel korundu. Kaynak test boyunca değişmedi; [script](review-evidence/review_sandbox_admission_crash.py), kaynak/image hash ve komut kayıtlıdır.
- Akış `create → full ID fsync/atomic replace → start --attach` olarak ayrıldı. Beş kontrollü süreç çökmesi testi, daemon ağ isteğinin keyfi gecikmesini veya host güç kaybını simüle etmez. Beş boş Docker sorgusu tek başına geciken bir oluşturma isteğinin yokluğunu kanıtlamaz; ID henüz kalıcı değilken geç kalan create yalnız başlamamış konteyner oluşturabilir. Belirsiz sahip/ID/image/dizin kimliğinde admission hata verir. Önceki yalnız Running senaryosunun [tarihsel kaydı](review-evidence/sandbox-admission-running-crash-historical.json) saklandı.

## Native worker kaynak sınırları

- [Host kontrolü](review-evidence/host-worker-limits-review.json), ayrı ve geçici bir `systemd-run --user` servisi içinde 128 MiB RAM, sıfır swap, %25 CPU ve 16 task sınırının gerçek cgroup dosyalarında uygulandığını doğruladı. RuntimeMax=10 saniye, TimeoutStop=2 saniye, KillMode=control-group, OOMPolicy=stop ve NoNewPrivileges aktiftir. Ana süreç normal çıkışından sonra `setsid` kullanan kendi çocuğu da kayboldu ve cgroup kaldırıldı.
- [Tekrarlanabilir script](review-evidence/review_host_worker_limits.py) yalnız 16 MiB bellek ayıran CPU fixture'ı çalıştırır; AOS, model, DB veya GPU'ya müdahale etmez. Bu profil gerçek Scorer/model bellek ihtiyacı veya timeout/OOM kabulü değildir; çalışan üründe exact unit sahipliği, kaynak bütçesi, süre aşımı ve stop/crash kanıtı ayrıca bağlanmalıdır.
- Native worker supervisor yalnız process-group'a güvenmemelidir: alt süreç ayrı session açabilir. Bu host üzerinde kendi exact cgroup'unu kapatmak, alt süreçlerin tamamını sınırlamak için uygulanabilir yoldur. API/Director kontrolü ayrı süreçte kalır.

- [Süre aşımı ve bellek sınırı kontrolü](review-evidence/host-worker-failure-review.json): yalnız iki test servisi 64 MiB RAM / sıfır swap / %25 CPU / 16 task ile çalıştırıldı. İki saniyelik RuntimeMax nedeniyle duran servis yaklaşık 2.07 saniyede; kasıtlı fazla tahsis nedeniyle kendi cgroup'unda OOM yaşayan servis yaklaşık 0.30 saniyede sonlandı. Exact unit journal kayıtları sırasıyla `timeout` ve `oom-kill` nedenlerini doğruladı. Her iki durumda ana/alt süreçlerin kalmadığı ve cgroup'un kaldırıldığı kontrol edildi; bağımsız CPU sentinel iki test boyunca yaşadı. [Script](review-evidence/review_host_worker_failure.py) yalnız kendisinin oluşturduğu süreçlere müdahale eder. Bu kontrollü hata testleri gerçek model birlikte kullanımında OOM olmaması kabulünün yerine geçmez.

- [Toplam kaynak sınırı kontrolü](review-evidence/host-aggregate-limits-review.json): worker başlamadan D-Bus ile oluşturulmuş UUID adlı geçici user slice altında iki ayrı CPU süreci eşzamanlı çalıştı. Her alt servis 96 MiB / 1 CPU / 16 task sınırına sahipken ortak üst cgroup 128 MiB / %25 CPU / 24 task ve sıfır swap sınırı uyguladı; gerçek cgroup dosyaları doğrulandı. İki worker exit 0 verdi, yalnız test slice/servisleri temizlendi. [Script](review-evidence/review_host_aggregate_limits.py), süreç başına limitin yanına toplam kaynak tavanı koymanın bu host üzerinde uygulanabilir olduğunu gösterir; henüz üretim Scorer supervisor veya model birlikte kullanım kabulü değildir.

- Üretim Scorer supervisor, worker/finalizer süreçlerini toplam 2 GiB RAM / sıfır swap / 1 CPU / 32 task sınırlı `swapp-ai-scientist-scorer.slice` altında başlatır; her başlatmadan önce gerçek cgroup dosyalarını doğrular. Kalan seed değerlendirme süresi 1–600 saniye parametresidir; tam Director bütçesine bağlama hâlâ açıktır. Ağır kütüphaneler yüklenmeden host flock alınır. [Ayrı süreç kontrolü](review-evidence/scorer-host-admission-review.json), kilit doluyken yaklaşık 38 ms'de `capacity_busy` döndüğünü ve bilerek olmayan credential dosyasının okunmadığını doğruladı. Bu kontrol veritabanı bağlantısının hesaplama ortasında kopmasını simüle etmez. CUDA_VISIBLE_DEVICES görünürlük filtresidir; OS aygıt ACL garantisi değildir.

### Kurulu vLLM için FP8 hazırlığı

- [Kaynak/header kontrolü](review-evidence/vllm-quantization-preflight.json), vLLM 0.30.0'ın kendi quantization registry'sinde `fp8_per_tensor` olduğunu, `bitsandbytes` olmadığını kaydeder. Eski sürümlerin BitsAndBytes örnekleri bu kurulu ortam için doğrudan kullanılamaz. [Güncel resmî online quantization belgesi](https://docs.vllm.ai/en/latest/features/quantization/online/) aynı FP8 scheme'ini tanımlar.
- Safetensors başlıklarından dil modeli + `lm_head` BF16 ağırlıkları 17,907,614,208 bayt olarak hesaplandı; vision/MTP hariç bile 16 GiB üstüdür. Bu, tam BF16 GPU yüklemesinin mevcut GPU'ya sığmayacağını gösterir. Kaynak metadata okuması GPU bellek ölçümü değildir.
- Kurulu online FP8 sınıfı ağırlıkları başlangıçta `meta` device üzerinde tanımlar ve yükleme sırasında dönüştürür. `--quantization fp8_per_tensor` brief'teki FP8 deneyi için hazırlanacak yoldur; bu kaynak özelliği gerçek startup peak veya sm_89 kernel başarısını tek başına kanıtlamaz. [İnceleme script'i](review-evidence/review_vllm_quantization.py) CUDA başlatmadan yalnız Python AST/text ve checkpoint header okur.
- Model boyutu, 32k bağlamda iki eşzamanlı dizinin sığması, S1/S2 throughput, parser/tool davranışı, prefix caching ve AOS ile sınırlı kaynak devri gerçek doctor koşusunda ölçülmelidir. Kısa bağlamda tek çağrı, 32k × 2 kabulünün yerine geçmez.
